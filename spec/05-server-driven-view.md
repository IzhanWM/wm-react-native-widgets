# 05 — Server Driven View

`ServerDrivenView` renders a screen described in JSON through a fixed catalog of
React Native components. The spec format follows Vercel's
[json-render](https://github.com/vercel-labs/json-render), so a spec written for
it — or generated by an LLM prompted with it — renders here with few changes.

Its purpose is **one app build, many screens**: bind `spec` to a variable and the
backend decides what each user, role or location sees. Example: a department
store's associate app serves an expiry sweep to Grocery, a demo-unit and
price-tag check to Electronics, and a size-run check to Apparel
(`UI Widgets/Server Driven View/Use Cases`).

## Files

| File | Role |
|---|---|
| `serverdrivenview.props.ts` | Public types — spec, element, events, component contract |
| `serverdrivenview.engine.ts` | React-free: spec normalization, paths, expressions, conditions, repeat |
| `serverdrivenview.catalog.tsx` | Built-in components (`SERVER_DRIVEN_COMPONENTS`) |
| `serverdrivenview.tsx` | Renderer: state, actions, recursion, `ref` handle |

One implementation on every platform; no peers beyond the root package's.

## Spec

```json
{
  "root": "card",
  "state": { "form": { "email": { "$data": "/user/email" } } },
  "elements": {
    "card":  { "type": "Card", "props": { "title": "Profile" }, "children": ["email", "save"] },
    "email": { "type": "TextInput", "props": { "value": { "$bindState": "/form/email" } } },
    "save":  { "type": "Button", "props": { "label": "Save" },
               "on": { "press": { "action": "saveProfile", "params": { "email": { "$state": "/form/email" } } } } }
  }
}
```

Also accepted: `{ "root": <node>, "state" }` or a bare node, where a node is
`{ type, key?, props, children: [node | "text"], visible, on, repeat }`; any of
these as a JSON string; any of these inside a Studio `{ dataSet }` wrapper.
Unparseable input renders an empty `View` — never a throw.

## Two sources: `data` and state

| | `data` prop | Local state |
|---|---|---|
| Holds | Bound Studio variables | UI state: form fields, toggles, picks |
| Read with | `{ "$data": "/p" }` | `{ "$state": "/p" }` |
| Written by | The page only | `$bindState`, `$bindItem`, state actions, `ref.setState` |
| On change | Re-renders live | Fires `onStateChange` |

State is **seed + edits**. The seed is `spec.state` resolved against `data`; edits
are replayed on top, one per path. So a field seeded from a variable fills in
when the variable loads late, and keeps the user's edit once they make one.
`resetState` drops the edits. A new spec (by content) starts fresh state; a new
object with the same content does not.

## Expressions

Any prop or action param may be one of these; paths are JSON pointers
(`/a/0/b`) or dotted (`a.0.b`), and `""` is the root.

| Expression | Value |
|---|---|
| `{ "$data": "/p" }` | Bound data |
| `{ "$state": "/p" }` | Local state |
| `{ "$bindState": "/p" }` | Local state, and the component may write it |
| `{ "$item": "field" }`, `{ "$item": true }` | Field of / whole current repeat row |
| `{ "$index": true }` | Current repeat index |
| `{ "$bindItem": "field" }` | Row field, writable when the rows live in state |
| `{ "$event": "member.name" }` | Payload of the event being handled |
| `{ "$template": "Hi ${$data/user/name}" }` | String; `${/p}` is state, `${$data/p}`, `${$item/f}`, `${$index}`, `${$event/f}` |
| `{ "$cond": c, "$then": a, "$else": b }` | Branch on a condition |

## Conditions (`visible`, `$cond`)

`true`/`false`; an array (all must hold); `{ "$and": [] }`, `{ "$or": [] }`,
`{ "$not": c }`; or a source (`$data`, `$state`, `$item`, `$index`) alone for
truthiness — empty arrays and strings are false — or with one of `eq`, `neq`,
`gt`, `gte`, `lt`, `lte`, `in`. `"not": true` inverts. Comparisons treat `1` and
`"1"` as equal, because Studio data often stringifies numbers.

```json
"visible": [{ "$state": "/form/email" }, { "$state": "/form/email", "neq": { "$data": "/user/email" } }]
```

## Repeat

`"repeat": { "statePath" | "dataPath" | "itemPath": "...", "key": "id" }` renders
the element's children once per row. `itemPath` reads a list inside the current
row (aisle → products). Rows go through `toRows`, so a variable wrapper or JSON
string works. Rows from state (or nested under rows from state) are writable via
`$bindItem`. Keys: `key` field, else `id`/`key`, else the index.

## Actions

`"on": { "<event>": { "action": "name", "params": {…} } }`, or an array run in
order — each sees the previous one's writes.

| Built-in | Params |
|---|---|
| `setState` | `statePath`, `value` |
| `pushState` | `statePath`, `value` — appends |
| `removeState` | `statePath`, `index` |
| `toggleState` | `statePath` |
| `resetState` | — |

Any other name goes to the `actions` prop's handler of that name, else fires
`onAction({ action, params, event, item, index, elementKey, state })`. In Studio,
switch on `event.action` and invoke **only** the variables you expect — a served
spec should not be able to reach arbitrary variables.

## Catalog

| Group | Types |
|---|---|
| Layout | `View`, `Row`, `Column`, `ScrollView`, `Pressable`, `Card`, `Spacer`, `Divider` |
| Content | `Text`, `Heading`, `Image`, `Badge`, `ListItem` |
| Input | `Button`, `TextInput`, `Switch`, `Checkbox`, `Stepper` |
| Feedback | `Spinner`, `ProgressBar` |
| Widgets | `QrCode`, `AvatarStack`, `SegmentProgress` (props pass through) |

Containers accept `gap`, `padding`, `align`, `justify`, `wrap`, `flex`,
`background`, `radius`, `width`, `height`; every type accepts `style`. Events:
`press`/`longPress` (`Button`, `Pressable`, `Card`, `ListItem`), `change`
(inputs; `submit`, `focus`, `blur` on `TextInput`), `select` (`AvatarStack`,
`SegmentProgress`), `error` (`QrCode`). Inputs are two-way through their value
prop (`value`, or `checked` on `Checkbox`); unbound, they keep a local value.

A type outside the catalog renders nothing (a red marker in `__DEV__`). Hosts
extend the catalog in code with `components={{ Rating }}`; a component receives
`{ props, children, emit, handles, bindings, element, elementKey, theme }`.
Gesture-root widgets (`SwipeDeck`, `ReorderList`) and optional-peer widgets
(`Maps`, `SkiaEffect`, `SignaturePad`) are left out so the subpath pulls in no
optional peer.

## WaveMaker Studio wiring

| Prop / event | Bind to |
|---|---|
| `spec` | A variable returning the screen, e.g. `Variables.sectionScreen.dataSet` |
| `data` | One variable's `dataSet`, or an object of several |
| `onAction` | Page handler: invoke a service variable, navigate, toast |
| `onStateChange` | Optional: copy edits into a variable as they happen |

Keep spec and data in separate variables: the spec changes per release of a
workflow, the data per minute.
